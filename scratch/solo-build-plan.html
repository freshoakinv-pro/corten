Founder Playbook

Building the four phases alone, with Claude Code as your only engineering pair.

A pragmatic playbook — how to translate the gap‑analysis roadmap into concrete daily work when there is no team, only you and an AI coding agent. Where scope has to shrink, where managed services replace ambitious infrastructure, what to delegate to Claude and what you must never delegate, and the exact first commands to run.

Companion doc. This playbook pairs with the gap analysis. That doc says what is missing; this one says how you build it, alone.

§ 01 The solo reframe

The original four‑phase plan assumed 2 – 3 senior engineers, a fractional CISO, and a market‑design lead from month one. You are one person. That fact does not change what Nervve must eventually become, but it does change three things about how you get there.

Scope shrinks hard. Two consoles instead of three; one pilot counterparty instead of a cohort; a rules‑based dispatcher long before any ML; manual settlement runs before automated payout. Every ambition the founder‑team plan carried gets deferred until it earns its keep.

Managed services replace ambitious infrastructure. Cloud Run in place of GKE; Firebase Auth in place of KeyCloak; Neon or Supabase in place of self‑managed Cloud SQL; Grafana Cloud in place of a bespoke observability stack. You will outgrow each of these — but "outgrow" is a good problem you get to have because the swap bought you 6+ months.

Claude Code is a force multiplier, not a substitute team. Well‑scoped it delivers roughly 2 – 3× throughput on engineering that is bounded and reviewable. It does not replace judgement, taste, sales, regulator dialogue, or being the person who is paged at 3am when a real dispatch fails. Your job is to be the architect, product owner, ops lead and sales team; its job is the code.

§ 02 What Claude Code does — and does not do

Solo operators fail with AI coding tools when they over‑trust them on the judgement work and under‑use them on the mechanical work. Draw the line explicitly and it stays useful.

Delegate freely

Mechanical, bounded, reviewable work.

  • Terraform modules from a written spec (VPC, GKE, Cloud SQL, KMS)
  • Boilerplate CRUD services once the domain model is fixed
  • Test scaffolding — unit, integration, contract tests from examples
  • Cross‑file refactors — renames, extractions, migration sweeps
  • Database migrations against a schema you review
  • Client SDKs and API adapters from OpenAPI or protobuf
  • CI / CD pipelines — GitHub Actions, Cloud Build, Cloud Deploy
  • Docs from code — READMEs, ADRs, runbook drafts
  • Multi‑file review passes via the /security-review and /simplify skills
Never delegate

Judgement, external trust, accountability.

  • The domain model. Energy‑market vocabulary is yours to author
  • The settlement rulebook. A wrong invoice is a customer you lose
  • Regulator conversations. EMA sandbox dialogue is your voice
  • Tech‑stack tradeoffs that lock you in for two years
  • Security accountability for CII — CCoP obligations name a person
  • On‑call at 3am. An AI cannot own a dispatch failure
  • First‑customer sales. Trust is bought with a founder's face
  • Hiring decisions when the time comes to add a first engineer
  • Handling counterparty data or bank details without an audit trail

§ 03 Scope resets by domain

Every domain from the gap analysis gets a solo swap — the ambitious choice deferred, the managed choice adopted, and a one‑line reason. Nothing here is permanent; each is a bridge you burn later.

§ 04 Your operating model with Claude Code

Solo throughput with an AI pair collapses without a working setup. Six patterns do most of the work — a well‑written CLAUDE.md, plan‑mode discipline, subagents for context hygiene, worktrees for parallel experiments, workflows for fan‑out, and MCP servers to reach your tools.

1
CLAUDE.md — your standing instructions

The single most important file in your repo.

Every Claude Code session reads it. It fixes conventions Claude would otherwise drift on, records your stack decisions, and lists the things it must never touch without asking.

# Nervve — CLAUDE.md

## Ownership
Solo founder. No teammates yet. You are my only engineering pair.
Optimise for: correctness, reviewability, small diffs, working tests.

## Stack
- Runtime: Node 22 + TypeScript, Cloud Run
- Data:    Neon Postgres 15 via Drizzle
- Events:  Cloud Pub/Sub with a single consumer per topic
- Auth:    Firebase Auth (interface abstracts for later swap)
- Infra:   Terraform (folder = env: dev / staging / prod)
- CI:      GitHub Actions → Cloud Run deploy on main

## Conventions
- Every service exposes /health and /ready.
- Every domain event has a schema in packages/events.
- Money is int64 cents. Currency codes are ISO 4217.
- Time is UTC ISO-8601 in code; local only at the edge.
- Tests: vitest for unit; playwright for e2e.

## Never do without asking
- Change anything under packages/settlement/rules/
- Modify Terraform in envs/prod/
- Delete data or migrations
- Add a new external SaaS without a written justification
- Skip tests to make CI green
2
Plan mode — your only code review

Design before you code. Every time.

You have no reviewer. Plan mode is the substitute — Claude drafts the change, you interrogate it, and only then does it execute. This is where architectural errors get caught cheaply.

# In an interactive Claude Code session:
/plan Add the deviation ledger table and the domain events for
DispatchAcknowledged and DispatchDeviated. The ledger must
be append-only, indexed by (site_id, window_id, event_time), and
survive out-of-order inserts. Show the migration, the event schema,
and the two publisher call-sites before writing anything.

If the plan is wrong, iterate the plan — not the code. Only exit plan mode when you would sign off on a colleague's proposal.

3
Subagents — protect the main context

Search, research and review without polluting your working memory.

The main conversation stays focused on the change you are shipping. Subagents do the digging and return only what you need.

# Explore — find where something lives
Use the Explore agent to locate every callsite of
SettlementRunFinalised across services.

# Plan — architectural design without touching files
Use the Plan agent to design the schema for the
half-hourly meter aggregation, keeping cardinality under
2M rows/day/site.

# Custom — your own energy-market analyst
# .claude/agents/market-analyst.md defines the persona
Use the market-analyst agent to check whether this
settlement window aligns with EMA's period definitions.
4
Worktrees — try two approaches at once

Parallel experiments without stomping on each other.

When you're not sure how to model something — a matching engine, a dispatch protocol — build both in isolated worktrees, run them side‑by‑side, and keep the winner.

# In Claude Code:
/EnterWorktree match-engine-orderbook
# build the continuous order-book variant

/EnterWorktree match-engine-callmarket
# build the periodic call-market variant

# Run both through the same test corpus, keep the
# winner, discard the worktree of the loser.
/ExitWorktree match-engine-orderbook # abandon
5
Workflows — fan out when the shape allows

Ten agents in parallel, on well‑bounded tasks.

Reviews, migrations, audits, and "same change across N files" work fan out well. Use only when you've explicitly asked for it — workflows spend tokens fast and are not the right tool for exploratory work.

# Say "ultracode" or ask for a workflow explicitly:
Use a workflow to run a CCoP-alignment audit across
every microservice under services/. For each service,
one agent checks:
  - Secrets access patterns
  - Logging of PII / meter data
  - Auth middleware present on all routes
  - TLS + mTLS on outbound calls
Adversarially verify each finding with a second agent
before reporting. Fan out; barrier only to dedupe.
6
MCP servers — reach your real tools

Wire Claude Code into GitHub, GCP, Sentry, Notion.

MCP is how Claude Code stops being just a code editor and becomes your operations console. The minimum solo set:

# Interactive setup: `/mcp` in Claude Code

github       # PR / issue / CI status without leaving the CLI
gcp          # deploys, logs, IAM checks
sentry       # pull the top errors before each deploy
linear       # or Notion — your single task list
postgres     # scoped read-only for prod investigation

# Never wire a write-capable MCP to a prod database
# without a WORM audit trail. Read-only is fine.

Hooks & skills — the last mile

Two more knobs make the difference between a novelty and a working operating environment. Skills package your repeated workflows into /slash‑commands; hooks enforce guardrails the model cannot skip.

# .claude/skills/ — your custom commands

/eod          # "end of day": summarise commits, test state, deploy log, open PRs
/settle       # run a settlement window and dump the reconciliation report
/preflight    # pre-deploy: run tests, tf plan, secrets check, changelog check
/dispatch-drill # fire the synthetic-meter harness and verify the dispatch loop end-to-end

# .claude/settings.json — hooks

SessionStart   # check node/pnpm versions, tf init, gcloud auth
PostToolUse    # run `pnpm lint --fix` after any Edit or Write
Stop           # enforce clean git tree before ending the session
PreToolUse     # block edits under packages/settlement/rules/ without confirm

§ 05 Phase 0 — Foundations · weeks 1 – 12

The single goal of Phase 0 is to make the rest of the work possible. You are laying rails: a domain model on paper, a repo you can grow into, cloud infra that Terraform owns, CI/CD that runs on every push, a settlement rulebook that describes the arithmetic before any code renders it, and an EMA conversation opened. No product yet.

Week 1 – 2

Repo, CLAUDE.md, first cloud contact

You + Claude

Start with the surfaces Claude will lean on for the next 18 months. Get the repo layout right and every session after this one becomes cheaper.

# Interactive Claude Code session in a fresh repo:

/init
# Bootstrap a monorepo with pnpm workspaces:
#   /apps/operator-console         (React + Vite)
#   /services/*                    (Cloud Run services)
#   /packages/events               (event schemas + zod validators)
#   /packages/domain               (aggregates, value objects)
#   /packages/settlement           (rulebook, ledger, tests)
#   /infra                         (Terraform, one folder per env)
#   /docs/adr                      (architectural decisions)
#   CLAUDE.md at root, per-package CLAUDE.md where useful

/plan A Terraform baseline for GCP in ap-southeast-1:
  - Private VPC, two subnets
  - Cloud Run enabled, Artifact Registry, Cloud KMS
  - Neon Postgres (external) connected via Cloud Run VPC connector
  - Secret Manager for all env config
  - Cloud Logging → BigQuery sink
  - IAM: three service accounts (dev, staging, prod), least-privilege
Output modular, apply incrementally, no click-ops.

By end of week 2: you can terraform apply a dev environment from a clean laptop, and pnpm dev boots a "hello world" Cloud Run service against Neon.

Week 3 – 4

Domain model & event catalogue — on paper

You lead · Claude drafts

This is the highest‑leverage work you will do all year. Get this wrong and everything downstream is expensive to fix. Do not let Claude author it — let it help you structure it.

# Use the Plan agent for pure design (no file writes):

Use the Plan agent to do an event-storming pass for a
two-sided grid-capacity marketplace. Identify:

  1. Aggregates (Counterparty, Site, Meter, Offer, Bid,
     Allocation, DispatchSignal, DeviationEntry, SettlementRun)
  2. Domain events per aggregate (past-tense, immutable facts)
  3. Command flows (who commands what, from where)
  4. Bounded contexts and where they seam

Return an ADR (docs/adr/0001-domain-model.md) and a Mermaid
diagram of the event flow. Do NOT write code.

By end of week 4: ADR 0001 signed off by you and your energy‑policy advisor. Every aggregate has a name that means the same thing to an energy person and an engineer.

Week 5 – 6

Settlement rulebook — on paper, then in tests

You author · Claude tests

The rulebook is a Markdown document that describes how allocations become invoices, how deviations are penalised, how netting works, how disputes are resolved. Write it. Then have Claude translate it into a test corpus that will run for the life of the platform.

# After you've drafted docs/settlement-rulebook.md:

/plan Read docs/settlement-rulebook.md. For every
numbered rule, generate:

  - A pure function in packages/settlement/rules/
    that implements it (int64 cents, no floats)
  - A property-based test (fast-check) covering the rule
  - A golden-file test with 3 - 5 hand-worked examples
    I will review before you commit

Do NOT invent rules. If a rule is ambiguous, list it
in docs/settlement-open-questions.md and stop.

By end of week 6: the rulebook is executable. You can hand it to a counterparty CFO and they can trace the arithmetic on a napkin.

Week 7 – 8

CI, security baseline, secrets discipline

Claude‑led

Every push runs the whole pipeline. Every commit is deployable. Every secret lives in Secret Manager. No exceptions, ever — solo founders die of shortcuts that only cost once.

/plan Write a GitHub Actions pipeline that on every push:

  1. Restores pnpm cache
  2. Runs lint / typecheck / test across the workspace
  3. Runs tf plan on any changed env folder
  4. Builds and pushes containers for changed services to
     Artifact Registry, tagged with the commit SHA
  5. On main: deploys to Cloud Run dev with the new tag
  6. Posts a PR comment with the tf plan diff and coverage

Then add a SessionStart hook that fails a Claude
session if git status is dirty or if any file
under infra/envs/prod was edited without a
matching ADR in docs/adr/.

By end of week 8: you cannot ship a commit without lint, test, tf plan, and deploy‑to‑dev all going green. If any of those hurt, fix the tooling, not the discipline.

Week 9 – 10

CCoP target document · fractional CISO onboarded

You + external

You do not need a running SIEM in Phase 0. You do need a written target‑state security architecture that a CCoP auditor could nod at. Retain a fractional CISO for ~4 hours a month to co‑author it and to sign off major decisions.

# Ask Claude to draft the skeleton before your first
# CISO session, so you're editing rather than authoring:

/plan Draft docs/security/target-architecture.md covering:

  - Asset inventory (services, data stores, secrets, IdPs)
  - Trust boundaries (public / private / OT)
  - Data classification (public, internal, meter, settlement, PII)
  - Encryption in transit and at rest (algorithms, key custody)
  - Identity, MFA, session, audit logging
  - Backup, DR, RPO / RTO targets
  - Incident response — first-hour runbook
  - CCoP 2.0 (Energy) control mapping — grid of controls
    with "have / partial / gap" status

Populate what our current infra supports. Mark everything
else as GAP with a proposed control.

By end of week 10: a real document exists. Your CISO has signed it. You are building the system it describes, not one Anyone will have to retrofit later.

Week 11 – 12

EMA sandbox conversation opened · Phase 0 close‑out

You alone

Regulator conversations are your job — no AI can carry them. Have your first structured EMA sandbox meeting on the calendar before Phase 0 ends. Turn up with the domain model, the rulebook, and the security target — three artefacts most sandbox applicants do not bring.

# Wrap-up automation you'll thank yourself for later:

Create a /eod skill that at end of every working day emits:
  - Commits shipped since last EOD
  - Test / coverage delta
  - Open PRs and their CI state
  - Deploy versions across dev / staging
  - Any file under packages/settlement/rules/ touched today
  - Any TODO added today

Pipe the output to a daily Notion page via the Notion MCP.

Phase 0 done when: the repo runs, CI ships to dev on every push, the domain and settlement docs are signed off, a fractional CISO is retained, and an EMA sandbox slot is on your calendar.

§ 06 Phase 1 — Closed pilot · months 3 – 12

One counterparty. One console. A rules‑based dispatcher. Manual settlement. The goal is a single successful trade end‑to‑end — offer, match, dispatch, measure, settle, invoice — witnessed by two humans on the counterparty side and yourself. Everything else is a distraction.

Month 3 – 4

Operator console · order book v1

Claude‑heavy

One console, three screens: order book (offers and bids), allocations, and dispatch log. No auth mystery — Firebase Auth, email login, one operator (you). Persistence is the boring Postgres of Phase 0.

/plan Build apps/operator-console as a React + Vite SPA
served by Cloud Run, protected by Firebase Auth.

Three routes:
  /book         — live offers & bids, WebSocket updates
  /allocations  — cleared allocations per window
  /dispatch     — signal history, ack state, deviation ledger

State: server-owned, no client cache beyond React Query.
Design system: shadcn/ui, minimal palette from the marketing site.
Ship behind operator.dev.nervve.io.

End of month 4: you can place a manual offer and bid, watch them match, and see the allocation in the console.

Month 5 – 6

Meter ingest · synthetic harness · dispatch loop

Claude + you

You need two ingest paths and one dispatch path. Build the synthetic one first — it is the safety net for every future test — then wire the real one to a single site.

/plan A synthetic-meter harness under services/harness:
  - Generates realistic half-hourly meter data
  - Publishes to Pub/Sub topic meter.reading
  - Configurable: site count, sample rate, noise, gaps
  - CLI: pnpm harness --sites 5 --rate 5m --hours 24

Then services/dispatch:
  - Consumes allocation.finalised
  - Emits dispatch.signal to a per-site channel
  - Waits for ack or times out (60s)
  - Writes to deviation_ledger if ack fails or measured
    delivery is outside tolerance

E2E test: harness → match → dispatch → measure → ledger,
using Playwright to drive the console.

End of month 6: the whole loop runs unattended on dev. You can leave it for an hour and come back to a full deviation ledger for the day's synthetic sites.

Month 7 – 8

Real meter for one site · SP Group path proven

You lead externally

The SP Group meter‑data authorisation path is not an engineering problem; it is a paperwork problem. Do the paperwork. Get one site's half‑hourly data flowing through the same Pub/Sub topic the harness uses, so the rest of the platform cannot tell the difference.

Month 9 – 10

Settlement run · manual payout · first real trade

You + counterparty

Run the settlement window against real meter data, generate the invoice PDF, hand it to the counterparty CFO, receive payment by bank transfer, reconcile in the ledger. This is your first real trade. Screenshot everything — you will pitch investors with it.

/settle --window 2026-11-01T00:00Z/2026-11-30T23:30Z

# Reads meter data, allocations, deviations from the
# window. Applies the rulebook. Generates:
#   - reports/2026-11.reconciliation.md
#   - invoices/*.pdf (one per counterparty pair)
#   - ledger entries (double-entry, WORM)
# Refuses to run if any deviation is unresolved.
Month 11 – 12

Second counterparty · pilot readiness review

You + fractional CISO

Second counterparty is the moment "one‑off" becomes "product". Also the moment your Phase 0 security document gets its first real audit — walk it with your fractional CISO, close the gaps that turned out to matter, and record what you deferred and why.

§ 07 Phases 2 & 3 — where solo ends

There is no version of Phase 2 you run alone. Regulated pilots, 24×7 dispatch, third‑party attestation and automated payout rails all require humans other than you. The playbook here is not code — it is the shape of the small team you'll assemble, and what Claude Code keeps doing while they arrive.

Phase 2 · Month 12

First engineer

You + 1

Backend generalist who can own the dispatcher and take the pager. Their onboarding artefact is CLAUDE.md + the ADR log — both were written for humans as much as for AI.

Phase 2 · Month 14

Retained SOC

+ external

A managed detection & response provider (in‑region, Singapore) begins ingesting your logs. Third‑party attestation of the CCoP target document starts.

Phase 2 · Month 16

Market‑design lead

+ 1 senior

You stop carrying EMA conversations alone. Fractional advisor becomes full‑time if the sandbox conversation graduates.

Phase 3 · Month 18+

SRE + full team

+ 3 – 5

On‑call rota, second APAC market, ISO 27001 / SOC 2 preparation. Claude Code stays — it is now every engineer's pair, not just yours.

Between now and month 12, Claude Code's job is to keep you shipping while you talk to regulators, counterparties, and the CISO. Every hour of your time saved on scaffolding is an hour that can go to the conversations only you can carry.

§ 08 Anti‑patterns to avoid

Five ways solo founders using AI heavily burn themselves. Each is easy to fall into, expensive to escape.

01
Letting Claude choose the stack. If you cannot articulate why Cloud Run over GKE, Neon over Cloud SQL, Drizzle over Prisma — you will re‑litigate the decision every three months. Own the choice, write it into an ADR, and move on.
02
Skipping tests because "Claude will catch it." Claude cannot catch what it has no reason to run. Tests are your only proof that today's Claude and last month's Claude agree on what the code should do. Solo means tests are non‑negotiable.
03
Writing settlement code without a written rulebook. The rulebook is Markdown you can hand to a lawyer or a CFO. The code is a rendering of it. If the code came first, you are one dispute away from re‑implementing everything.
04
Standing up self‑hosted infrastructure "because it's cheaper." A self‑hosted KeyCloak or Kafka cluster is a full‑time job you don't have. Every hour you spend on it is an hour not spent on customers or the rulebook. Managed services are your compensation for having no ops team.
05
Deferring the fractional CISO until you have a product. CCoP is a regime you build into or retrofit into. Retrofit costs 3 – 5× build‑in cost, and the retrofit conversation with an EMA sandbox lead is the wrong first impression to make.
