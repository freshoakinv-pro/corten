Solutions Architecture

From marketing site to market operator: what stands between today and a live, regulated grid‑capacity platform.

A structured assessment of the Nervve platform's current state against a mature, production‑grade reference — benchmarked to the Pyxis GCP architecture the founders used before, and extended with the demands specific to a two‑sided grid marketplace: OT integration, real‑time dispatch, financial settlement, and CII‑grade cyber posture in Singapore.

§ 01 Executive summary

The corten repository currently contains a well‑crafted marketing website and nothing more — no backend, no data ingest, no matching engine, no settlement, no authentication, no observability, no infrastructure‑as‑code. The site accurately describes what Nervve will be; the platform that would deliver those promises does not exist in this codebase. Against a mature live reference, ~13 of 14 platform domains require net‑new build. The Pyxis architecture is a reasonable spine to reuse — but a grid‑capacity marketplace layers on four dimensions Pyxis did not need: OT/telemetry ingest, real‑time dispatch, financial‑grade settlement, and CII‑tier cyber governance.

§ 02 Method & scope

What was inspected, and what "current state" and "target state" mean in this document.

Scope caveat Current state is derived exclusively from the freshoakinv-pro/corten repository — two HTML files, one SVG logo, one favicon. If Nervve platform code exists in another repository or environment (a Flutter mobile app, a Node/Java backend, Terraform in a private repo, an existing GKE cluster), it was not visible during this assessment, and gaps below should be re‑graded once that surface is disclosed. Target state is what a live, regulated, revenue‑generating grid‑capacity marketplace needs to operate against Singapore's EMA framework and CSA CCoP 2.0 obligations for Critical Information Infrastructure — with the Pyxis GCP architecture as a like‑for‑like technology spine where the fit is direct.

§ 04 Category detail

Each domain expands into the concrete deltas between what exists and what a mature live platform requires, and the first move that should be made against it.

01

Frontend applications

Critical
Current

A single marketing microsite: index.html, resources.html, one hero canvas animation. No authenticated surface, no state, no product screens.

Target
  • Capacity‑Holder console — offer curves, revenue statements, dispatch history
  • Capacity‑Buyer console — bid entry, allocation view, invoices
  • Operator / Admin console — order book, dispatch overrides, KYC, incident switchboard
  • Design system with accessibility floor (WCAG 2.2 AA)
  • Framework: React + TS (web‑first), Flutter only if a mobile‑app surface is truly warranted
Recommended first move Design‑sprint the three consoles in low‑fi before writing any code, then stand up the Buyer console first — it is the shortest path to onboarding a paying counterparty and forcing the backend to become real.

02

Backend microservices

Critical
Current

Zero services. The join form does not post to any server — it opens the visitor's mail client via mailto:.

Target
  • Identity · sessions, RBAC, delegated‑access consent
  • Party & Asset · counterparties, sites, meters, DERs
  • Capacity Book · reservations, offers, bids, allocations
  • Matching & Clearing · order book, market‑maker, price discovery
  • Dispatch · signals to DERs, ack/nack, deviation tracking
  • Settlement · double‑entry ledger, netting, invoicing, payouts
  • Notifications · Firebase Cloud Messaging, email, SMS, webhooks
  • Deployed on GKE per Pyxis pattern; Java/Spring or Node/TS, gRPC or REST + async via Pub/Sub
Recommended first move Draft the domain map and event catalogue (~15 aggregates, ~40 events) before choosing a language — the shape of the ledger and the dispatch loop dictates the runtime more than the reverse.
4 / 4
03

Identity & access management

Critical
Current

No auth. No user store. No secrets. Any "join" is an email intent.

Target
  • KeyCloak (as Pyxis) or Google Identity Platform as the OIDC IdP
  • MFA mandatory for every operator‑ or dispatch‑privileged role — hardware‑key backed for admins
  • RBAC on API + ABAC (attribute‑based) on data rows for multi‑tenant isolation
  • Singpass / Corppass federation for Singapore counterparty onboarding
  • SCIM provisioning; audit log every privilege change to WORM storage
Recommended first move Adopt Google Identity Platform + Firebase Auth first for pilot speed, but design the abstraction so a swap to KeyCloak or Auth0 for CII hardening is a config change, not a rewrite.
4 / 4
04

Data platform (OLTP, warehouse, timeseries)

Critical
Current

No database, no schema, no migrations, no warehouse. The site is stateless.

Target
  • OLTP · Cloud SQL for PostgreSQL, HA + regional replicas, PITR, encrypted at rest with CMEK
  • Timeseries · Bigtable or TimescaleDB for meter/telemetry (millions of points/day per site)
  • Warehouse · BigQuery for analytics, dbt for modelling, event‑sourced settlement fact tables
  • Object store · GCS with lifecycle rules, immutable retention on settlement artefacts
  • Schema governance · migrations via Liquibase or Atlas, dictated by dispatch/settlement correctness needs
Recommended first move Pick the timeseries store first, not last — meter cardinality & retention economics will shape every downstream ingest and settlement decision.
4 / 4
05

Streaming & real‑time

Critical
Current

None. The site is static; nothing arrives, nothing is emitted.

Target
  • Pub/Sub for asynchronous domain events (offer/bid/allocation/dispatch/settlement)
  • Dataflow (Apache Beam) for meter‑stream aggregation, gap fill, quality tagging
  • Sub‑second dispatch path with idempotent commands and deterministic replay
  • Ordered event log (Kafka or Pub/Sub Lite) for audit reconstruction — regulator‑grade traceability
Recommended first move Stand up a synthetic meter‑stream harness to prove ingest, dispatch, and settlement round‑trip end‑to‑end before wiring a single real DER.

06

Grid & OT integration — NEW vs. Pyxis

Critical
Current

No integrations of any kind. No adapters, no gateways, no protocol stacks.

Target
  • Meter data · SP Group half‑hourly and 5‑minute feeds via authorised API
  • Market feeds · EMA / EMC price and dispatch schedules (USEP, LCP)
  • DER control · IEEE 2030.5 (SEP2) & OpenADR 2.0b for demand response and DERs
  • Substation / OT · IEC 61850 / DNP3 gateways where behind‑the‑meter industrial loads participate
  • Edge · a hardened field gateway pattern for sites with intermittent WAN — buffered, signed telemetry
  • Segregation · IT/OT boundary with unidirectional gateway or brokered mediation, IEC 62443 zoning
Recommended first move Lock the SP Group meter‑data authorisation path first — access, latency, and cost of that feed decide whether behind‑the‑meter is even a viable pilot topology in year one.
4 / 4
07

Matching, dispatch & settlement — NEW vs. Pyxis

Critical
Current

Described on the site as "matches supply to demand, prices it fairly and settles it automatically". No code exists.

Target
  • Order book · continuous or periodic call market, configurable by product
  • Clearing · price discovery with locational and network‑constraint awareness
  • Dispatch · signal → ack → measure → deviation ledger, with fail‑safe local set‑points
  • Settlement · double‑entry ledger, netting, tax, invoicing, payout to bank; reconcile against USEP where applicable
  • Audit · every decision reproducible from the event log; regulator‑ready trade blotter
  • Financial rails · GIRO/FAST or PSP integration (Stripe/Airwallex) with bank‑grade reconciliation
Recommended first move Write the settlement rule‑book before the matching engine. If two counterparties can't agree on the invoice arithmetic on paper, code will not save them; when they can, the engine becomes a rendering of an agreed spec.

08

AI / ML orchestration

Critical
Current

None. Site copy foregrounds AI orchestration ("AI that orchestrates the whole network") — no models, no pipelines, no registry.

Target
  • Forecasting · load, DER availability, price — retrained on schedule with drift alerts
  • Optimisation · Model‑Predictive Control (MPC) for dispatch under grid constraints
  • Feature store · Vertex AI Feature Store or Feast for training/serving parity
  • Model governance · registry, lineage, canary rollouts, human‑override kill switches
  • Guardrails · every automated dispatch bounded by safe operating envelopes with hard‑coded overrides
Recommended first move Ship a deterministic rules‑based dispatcher first; earn the right to introduce ML once the settlement rulebook is stable and the telemetry corpus is real.

09

Cybersecurity & CII posture — NEW vs. Pyxis

Critical
Current

Static hosting only. Not a security posture — it is the absence of one. Beyond browser TLS from GitHub Pages, nothing is architected.

Target
  • Frameworks · CSA CCoP 2.0 alignment (Energy sub‑sector), IEC 62443 for OT, NIST CSF 2.0 for enterprise
  • Keys · Cloud KMS with CMEK, envelope encryption; HSM‑backed signing for dispatch commands
  • Network · private VPC, Cloud Armor at edge, mutual TLS between services, egress deny‑by‑default
  • Boundary · IT/OT DMZ with brokered mediation; jump hosts; no operator laptop touches OT directly
  • Detect & respond · SIEM (Chronicle or Splunk), 24×7 monitoring by pilot end, quarterly red‑team, IR runbooks, tabletop drills
  • Governance · CISO‑equivalent function from month one, third‑party attestation before first live dispatch
Recommended first move Commission a CCoP‑aligned target‑state security architecture in parallel with product design — retrofitting CII controls is materially more expensive than building to them.

§ 05 Where the Pyxis blueprint carries — and where it doesn't

Reusing the founders' prior architecture accelerates the enterprise scaffolding. It says nothing about the four domains that make Nervve a grid‑market operator rather than a booking app.

Reuses cleanly from Pyxis

The enterprise scaffolding transfers.

  • GKE as the workload substrate for microservices
  • Cloud SQL (Postgres) as the OLTP store
  • KeyCloak as the identity broker
  • Cloud Load Balancing + Cloud Armor at the edge
  • Cloud Build / Cloud Deploy / SonarQube / Binary Authorization as the delivery pipeline
  • Cloud Logging / Monitoring / Error Reporting for observability
  • Firebase Cloud Messaging for notifications
  • Private VPC, Cloud IAM, KMS, Command Center as the security floor
Net‑new for Nervve

Four domains Pyxis never needed.

  • Streaming ingest — Pub/Sub, Dataflow, timeseries store; meter data is nothing like booking data
  • OT integration — IEC 61850, DNP3, IEEE 2030.5, OpenADR, field gateways, IT/OT boundary
  • Financial‑grade matching & settlement — order book, clearing, double‑entry ledger, invoicing, payouts, regulator‑ready audit
  • CII cyber posture — CCoP 2.0 + IEC 62443, HSM‑backed signing, SIEM, 24×7 monitoring, red‑team cadence, DPO/CISO governance

§ 06 Sequenced roadmap

Four phases, each earning the right to the next by proving something concrete. Timelines assume a small, focused engineering team (see next section).

Phase 0

Foundations

Months 0 – 3
  • Domain map + event catalogue
  • Terraform baseline on GCP
  • KMS, IAM, VPC, private GKE cluster
  • CI/CD scaffolding, Binary Authorization
  • CCoP‑aligned security target document
  • Settlement rule‑book v1 (on paper)
  • EMA sandbox engagement opened
Phase 1

Closed pilot

Months 3 – 9
  • Buyer + Operator consoles v1
  • Rules‑based dispatcher (no ML yet)
  • Deterministic matching engine
  • Ledger + invoicing (manual payout)
  • Meter ingest for 1 – 2 pilot sites
  • SP Group data path proven
  • Observability floor + on‑call
Phase 2

Regulated pilot

Months 9 – 18
  • Multi‑counterparty pilot under EMA sandbox
  • Automated payout rails
  • Deviation ledger & settlement audit
  • Full CCoP alignment + third‑party attest
  • Warehouse + first BI dashboards
  • Holder console + self‑serve statements
  • First forecast/optimisation models in shadow
Phase 3

Scale & travel

Months 18 – 30
  • MPC dispatcher in production w/ overrides
  • Regional multi‑site, multi‑tenant
  • SIEM + 24×7 monitoring
  • Certifications: ISO 27001, SOC 2
  • Second‑market playbook (an APAC grid)
  • Partner API for retailers & DERMs
  • Quarterly red‑team cadence
